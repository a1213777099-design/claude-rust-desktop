# 请求体超限根治计划：后端派生对话历史（对齐开源项目架构）

> 目标版本：2.1.13
> 核心问题：**开源项目（Codex / Claude Code / DeepSeek Harness）持续聊几百条也不会碰到"请求体超 2MB"的问题，它们是怎么设计的？本项目如何对齐。**

***

## 一、业界答案：开源项目为什么不触发 body 限制

调研结论（Codex CLI 源码分析、dsh 官方架构文档、Claude Code 反编译文档）：

### 1. 它们根本不通过 HTTP 传输对话历史

| 项目                     | 架构           | 历史如何到达 LLM                                                             |
| ---------------------- | ------------ | ---------------------------------------------------------------------- |
| Codex CLI              | 单进程 Rust CLI | 历史（rollout.jsonl）在进程内存中，agent loop 直接组装请求发给模型 API，**没有"前端→后端"HTTP 环节** |
| Claude Code            | 单进程 Node CLI | 同上，历史在内存 + transcript 文件，进程内组装                                         |
| DeepSeek Harness (dsh) | 本机 CLI/SDK   | **Session log 是唯一事实源**，`deriveMessages()` 在后端从 log 投影出模型历史             |
| dsh Web 模式（前后端分离）      | 后端持历史        | Web 前端**只发增量输入**（新消息文本），后端从 session log 派生完整上下文                        |

**共同点：历史持有者 = LLM 调用者 = 本地存储读取者。对话历史永远不跨进程传输。**

dsh 的设计哲学原文："The session log is the source of the context the model sees. `deriveMessages()` projects model history from it."（会话日志是模型所见上下文的唯一来源，模型历史是从日志**投影**出来的）

### 2. 发给模型的请求也不会无限膨胀

即使进程内组装，Codex 在发给 LLM 前还有两道闸门：

- **工具输出瘦身**：超限时从尾部往回把大工具输出替换为占位符（"Output exceeded… truncated"）

- **compaction**：上下文满时压缩为摘要，用户消息 verbatim 保留（从最新往回 64k token 预算内全保）

### 3. 本项目的根本问题

本项目是**前后端分离**（React 前端 + Rust bridge 后端），但采用了"前端传全量历史"的错误模式：

```
现状（错误模式）：
前端 ──HTTP POST 全量历史(2.3MB, 含UI字段)──▶ 后端 ──透传──▶ 模型
        ↑ 413 根因：跨进程传了不该传的东西

业界模式（dsh 投影架构）：
前端 ──HTTP POST 新消息(几KB)──▶ 后端 ──从DB读取──▶ 投影裁剪 ──▶ 模型
```

**关键事实：后端本来就有完整 DB**（messages 表 + tool\_calls 表），`GET /api/conversations/{id}` 已经在从 DB 读取并聚合历史（bridge/mod.rs L954-989）。前端发送 messages 是**纯冗余传输**。

## 二、方案：改造为后端派生历史（dsh 投影模式）

### 数据流对比

| 场景    | 现状（前端传历史）                                 | 改造后（后端派生）                                         |
| ----- | ----------------------------------------- | ------------------------------------------------- |
| 普通发送  | body = 全量历史 + 新消息（2.3MB）                  | body = `conversation_id + message + model`（< 2KB） |
| 重试    | 先 DELETE 后端消息，再发 `[...slice(0,idx), 新消息]` | 先 DELETE（DB 已是正确状态），再发纯新消息；后端读 DB 自动得到正确历史        |
| 编辑重发  | 同上                                        | 同上                                                |
| 新会话首条 | body = 1 条消息                              | 同样 1 条，行为不变                                       |
| 会话越长  | body 无限膨胀 → 413                           | **body 恒定小，永不触发**                                 |

**重试场景正确性论证**：前端重试前已调用 `DELETE /messages/{mid}`（删 idx 及之后所有消息，tool\_calls/attachments 靠 FK ON DELETE CASCADE 级联）。DB 此时恰好等于"idx 之前的历史"。后端读 DB + 追加新 message = 与现在前端传 `[...messages.slice(0, idx), tempUserMsg]` 完全等价。

**已验证的支撑事实**（探索确认）：

- `conversation_get` 已有完整的 DB 读取 + tool\_calls 聚合代码，直接复用（bridge/mod.rs L954-989）

- engine 用户消息入库带去重逻辑（engine\_core.rs L484-504），从 DB 派生后新消息仍会正确入库

- `build_openai_messages` 读取 `role/content/tool_calls/toolCalls/tool_call_id` —— DB 聚合输出恰好是 `tool_calls` 格式（id/name/input/output/is\_error），天然兼容

- compact 生成的摘要消息（is\_compact\_boundary=1）存在 DB，后端读取时自然带上

## 三、改动清单

### 3.1 后端：chat\_handler 从 DB 派生历史（核心改动）

**文件：`src-tauri/src/bridge/mod.rs`** **chat\_handler（L575 起）**

1. 将 `conversation_get`（L954-989）中的 DB 读取 + tool\_calls 聚合逻辑抽成可复用函数：

   ```rust
   async fn load_conversation_history(state: &AppState, conv_id: &str) -> Vec<serde_json::Value>
   // 返回 [{id, role, content, tool_calls?}]，即现有 conversation_get 的 messages 数组
   ```
2. chat\_handler 中替换：

   ```rust
   // 旧：let messages = req.get_messages();
   // 新：
   let mut messages = load_conversation_history(&state, &conv_id).await;
   if let Some(msg) = &req.message {
       messages.push(serde_json::json!({ "role": "user", "content": msg }));
   }
   ```
3. `ChatRequest` 结构体删除 `messages` 字段及 `get_messages()` 方法（L77、L92-107）——彻底移除该传输通道

### 3.2 后端：删除用户消息入库的去重补偿逻辑

**文件：`src-tauri/src/native_engine/engine_core.rs`（L484-504）**

- 现有逻辑：入库前 `SELECT COUNT(*) WHERE role='user' AND content=?`，存在则跳过

- 该去重是为旧模式（前端传全量历史，engine 无法区分新旧消息）设计的补偿，且现存 bug：用户重发相同内容（如连续两次"继续"）会被错误跳过入库

- 新模式下 chat\_handler 传入的 DB 历史不含新消息，`user_messages.last()` 必为新消息，直接插入即可

- 改动：删除 existing 计数检查，保留插入

### 3.3 后端：Anthropic 路径补窗口化 + 阈值动态化

**文件：`src-tauri/src/native_engine/tool_loop.rs`**

后端成为上下文组装唯一责任方后，必须保证发给模型的不超窗（现状 Anthropic 路径零截断）：

1. `build_anthropic_messages()`（L1197-1242）开头调用 `windowed_history()`（与 OpenAI 路径 L1246-1268 相同）
2. `windowed_history()` 阈值从固定 `120_000` chars 改为按模型推导：

   ```rust
   let ctx_tokens = crate::native_engine::provider_manager::get_default_context_size(model_id);
   let max_chars = ((ctx_tokens as f64) * 0.6 * 2.0) as usize; // token→char 粗算，留 40% 余量给输出
   let max_chars = max_chars.max(60_000); // 保底
   ```

### 3.4 前端：停止发送 messages 数组

**文件：`src/api.ts`** **+** **`src/components/MainContent.tsx`**

1. `sendMessage`（L1782）：删除签名中的 `messages?: any[]` 参数；body 中删除 `messages: ...` 行（L1837）
2. `sendMessageNative`（L1566）：同步删除 `messages` 传参（body L1612）——保持两个入口一致
3. 三个调用点删除最后一个实参：

   - MainContent.tsx L3018（handleSend）：删 `[...messages, tempUserMsg]`

   - MainContent.tsx L3606（handleResendMessage）：删 `[...messages.slice(0, idx), tempUserMsg]`

   - MainContent.tsx L3825（handleEditSave）：删 `[...messages.slice(0, idx), tempUserMsg]`

### 3.5 版本号与重启（用户规则）

- `package.json` / `src-tauri/tauri.conf.json` / `src-tauri/Cargo.toml`：2.1.12 → **2.1.13**

- 重启 dev 后端（`npm run dev:stable`，增量编译约 5-15 分钟）

## 五、明确不做（本次排除）

| 排除项                        | 理由                                             |
| -------------------------- | ---------------------------------------------- |
| Codex 式服务端加密摘要 blob        | 依赖 OpenAI 专有 API，本项目多 provider                 |
| LLM 智能摘要压缩（升级现有规则 compact） | 解决的是"上下文窗口满"而非"请求体超限"，窗口化（3.3）已保证不超窗；留作下版本独立任务 |
| token 估算修正（×1.5 高估）        | 独立小问题（影响 auto-compact 误触发），与 body 无关，留作下版本     |
| prompt cache 优化            | 独立话题，后续单独立项                                    |
